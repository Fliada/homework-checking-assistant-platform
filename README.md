# Avito AI Reviewer

Платформа проверки домашних работ: React 19 + TypeScript + Vite, FastAPI, SQLAlchemy, Celery. Основной канал сдачи — GitHub Pull Request. Ревьюер подтверждает оценки и замечания; студент получает только подтверждённый результат.

## Быстрый запуск на macOS / Linux

Нужны Node.js 22.12+ или 24 и Python 3.11+ (Docker использует Python 3.12).

Выполните из корня репозитория:

```bash
npm ci
npm run setup
npm run dev
```

- Интерфейс: http://127.0.0.1:5173
- API и интерактивная документация: http://127.0.0.1:8000/docs
- Проверка API: http://127.0.0.1:8000/health
- Остановка интерфейса и API: `Ctrl+C`.

`setup` устанавливает Python-зависимости в `backend/.venv` и, если `.env` ещё нет, создаёт его с уникальными секретами. Существующий `.env` не перезаписывается. Для первого локального запуска включены `APP_DEBUG=true` и `SEED_DEMO=true`: на странице входа доступны демонстрационные аккаунты. Переключение ролей существует только в режиме разработки. Owner создаётся из `OWNER_EMAIL`, `OWNER_PASSWORD` и `OWNER_NAME` в `.env`; назначать администратора может только Owner.

Локальный запуск использует SQLite в `backend/reviewer.db` и фоновые задачи внутри процесса API. PostgreSQL и Redis для этого режима поднимать не нужно. Данные сохраняются после перезапуска. База, артефакты, зависимости и секреты исключены из Git.

Если нужен только один процесс, используйте отдельные терминалы:

```bash
npm run dev:backend
```

```bash
npm run dev:frontend
```

`frontend/index.html` — входной файл сборщика, а не самостоятельная HTML-страница. Его нельзя запускать через `file://`: браузер не компилирует TypeScript/JSX и не разрешает такие импорты модулей. Открывайте HTTP-адрес выше. Исходный корневой `index.html` сохранён как UX-прототип и не используется приложением.

## PostgreSQL, Redis и Docker Compose

Подготовьте `.env` через `npm run setup` либо скопируйте `.env.example`, задав собственные `JWT_SECRET`, `OWNER_PASSWORD` и `POSTGRES_PASSWORD`.

```bash
docker compose up --build -d
docker compose logs -f api worker
```

Интерфейс доступен на http://localhost:5173. Nginx отдаёт сборку и проксирует `/api/` в FastAPI. Compose запускает PostgreSQL 16, Redis 7, API и Celery worker; база и артефакты находятся в volumes. Для остановки: `docker compose down`.

Перед публичным запуском задайте `APP_DEBUG=false`, `SEED_DEMO=false`, настройте HTTPS и разрешённые источники. Первый Owner берётся из переменных окружения. Демонстрационные аккаунты предназначены только для отдельной локальной базы разработки.

## GitHub Pages: автоматическая публикация интерфейса

GitHub Pages обслуживает статические HTML/CSS/JS. Python API, worker, PostgreSQL и Redis требуют отдельного сервера. Поэтому публикация состоит из двух частей:

1. Разверните backend, например через Docker Compose на своём сервере с HTTPS. Адрес API должен быть доступен браузеру пользователя.
2. В GitHub откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**.
3. Откройте **Settings → Secrets and variables → Actions → Variables** и создайте переменную `VITE_API_URL`, например `https://reviewer-api.example.org/api/v1`. Это публичный адрес, а не секрет.
4. На backend добавьте домен Pages в `CORS_ORIGINS`, например `https://your-login.github.io`, и перезапустите API. Путь репозитория в CORS не указывается.
5. В **Settings → Environments → github-pages** разрешите деплой ветки `codex/service`, если включены ограничения веток.
6. Закоммитьте и отправьте изменения в `codex/service`. Workflow `.github/workflows/pages.yml` автоматически выполнит `npm ci`, сборку и публикацию `dist`. После появления workflow в основной ветке его также можно запускать вручную через Actions.

Workflow определяет базовый путь Pages автоматически и собирает приложение с hash-маршрутами, поэтому ссылки вида `https://your-login.github.io/repository/#/ledger` работают после обновления страницы. Без `VITE_API_URL` workflow завершится с понятным сообщением, чтобы не публиковать интерфейс с неработающим относительным `/api`.

Ни `.env`, ни `OPENAI_API_KEY`, ни исходники backend в Pages не загружаются. В `VITE_*` можно указывать только публичную конфигурацию: эти значения встраиваются в JavaScript. Секреты остаются в окружении backend.

Локальная проверка сборки:

```bash
npm run build
npm run preview
```

Откройте http://127.0.0.1:4173; для запросов API backend должен работать на порту 8000.

Документация: [GitHub Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [публикация Vite](https://vite.dev/guide/static-deploy.html#github-pages).

## Gemma через Google AI Studio и GitHub

По умолчанию проверки используют `gemma-4-31b-it` через Gemini API. Создайте ключ в [Google AI Studio](https://aistudio.google.com/apikey) и заполните существующий `.env` в корне репозитория:

```dotenv
GEMINI_API_KEY=your-google-ai-studio-api-key
GEMMA_MODEL=gemma-4-31b-it
ALLOW_PUBLIC_LLM=true
```

Перезапустите API после изменения ключа: при локальном запуске остановите `npm run dev` через `Ctrl+C` и запустите снова. Для Docker выполните `docker compose up -d --force-recreate api worker`, чтобы оба процесса получили обновлённое окружение.

Войдите как Owner или Admin и откройте **Модели и настройки → Настроить**:

| Поле                          | Значение                                           |
| ----------------------------- | -------------------------------------------------- |
| Провайдер                     | Gemma · Google AI Studio (`gemini`)                |
| Base URL                      | `https://generativelanguage.googleapis.com/v1beta` |
| Имя модели у провайдера       | `gemma-4-31b-it`                                   |
| Переменная окружения с ключом | `GEMINI_API_KEY`                                   |
| Формат ответа                 | JSON по инструкции                                 |

Ключ вводится только в серверный `.env`; в форме указывается имя переменной. Кнопка **Проверить** запрашивает сведения о выбранной модели и проверяет доступ к `generateContent` без генерации. Полный вызов модели происходит при запуске проверки работы. Доступные Gemma-модели описаны в [документации Google](https://ai.google.dev/gemma/docs/core/gemma_on_gemini_api).

`GEMMA_MODEL` задаёт имя модели только при первоначальном создании демо-каталога. Для существующей базы изменяйте модель через форму: сохранённые настройки не перезаписываются при старте. Старый внутренний ID `openai-default` сохранён для совместимости привязок заданий; провайдер и название определяются полями записи.

Gemma получает схему JSON в инструкции, а backend проверяет структуру ответа и ссылки на исходные фрагменты. Неполный, заблокированный или невалидный ответ не превращается в фиктивную оценку. Модели OpenAI и локальные совместимые endpoints также доступны в каталоге; для них задаётся собственная переменная с ключом.

- При необходимости в `.env` добавьте `GITHUB_TOKEN`. Для публичных PR он повышает лимиты GitHub API. `GITHUB_WEBHOOK_SECRET` нужен только при подключении webhook, а не при ручной отправке ссылки.
- Эксперт выбирает конкретные модели для этапов задания, создаёт черновик конфигурации, запускает оценивание на примерах и публикует версию. Опубликованная версия неизменяема; старые проверки сохраняют привязку к своей версии.
- Без настроенной модели или ключа остаётся доступна ручная проверка. Агент не генерирует фиктивные баллы, уверенность или метрики.
- В `dev_demo` публичные endpoints Google и OpenAI разрешены только для подтверждённо публичных данных. В чувствительном режиме используются только разрешённые приватные endpoints. Подробности — в `backend/PIPELINE.md`.
- Весь модуль выявления использования ИИ заменён заглушкой. Поиск в интернете, OCR и исполнение студенческого кода не выполняются.

Публичные условия GO/task1, task2, task3 и ссылки на примеры закреплены в `backend/fixtures` по коммиту исходного [homework_examples](https://github.com/ai-talent-hub-avito/homework_examples). Три задания имеют отдельные рубрики. Демо-работы и пользователи синтетические, результаты eval до запуска отсутствуют.

## Проверка кода

```bash
npm run build
cd backend
.venv/bin/python -m pytest tests -q
```

Тесты пользовательских сценариев интерфейса: `npm test` из корня репозитория.

Серверные тесты используют отдельную тестовую SQLite-базу и замоканные внешние HTTP-вызовы. Они не отправляют данные в Google или OpenAI и не расходуют токены.
