# **Context Pack — Avito AI Reviewer**

Обновлён: 3 сентября 2026\. Полный разбор: avito\_ai\_reviewer\_product\_case.md.

## **1\. Проблема одной фразой**

**Ситуация:** вечер, у ревьюера 12 непроверенных работ в трёх разных системах, а проверка — не его основная работа. 

**Хочу:** дать честную оценку и полезный фидбэк каждому. 

**Чтобы:** не потратить полдня, не перечитывать критерии заново и не подвести студента со сроком.

Чья это работа: **ревьюер** (эксперт Авито или приглашённый) — основной носитель проблемы. Рядом методист (готовит задание и критерии), организаторы программы (распределяют, ведут ведомость и сроки) и студент (ждёт результат).

Что оптимизируем: не «часы ревьюера», а **долю работ, по которым студент получил качественную обратную связь в срок**. Часы — ресурс, а не цель.

## **2\. Как это делают сейчас и что это стоит**

Полностью вручную, поверх трёх чужих платформ, и роли при этом разнесены.

**Методист** составляет задание и формирует критерии к нему. 

**Организаторы (команда образования)** формируют группы студентов и назначают их конкретным ревьюерам, заводят ведомость в Google Sheets, назначают дедлайны для всех, проводят перед началом проверки координирующую встречу для сверки критериев и проговаривают отношение программы/курсы к использованию ИИ. 

**Студент** выполняет работу на сторонней платформе — Stepik, GitHub или Google Docs в зависимости от специфики задания — и отправляет её на проверку чаще всего через ту же платформу. 

**Ревьюер** был на координирующей встрече один раз перед началом проверки, дальше работает один: оценивает по критериям и по собственным ощущениям. В момент проверки у него открыто одновременно четыре вкладки — ведомость в Google Sheets, документ с критериями, документ с фидбэком для студента и сама работа. И так по каждому студенту, а студентов много.

* Эксперт: **5–10 часов в неделю**. Поддержка процесса со стороны команды образования: **до 10 часов в неделю**.  
* Модель процесса: **15 шагов на одну работу, 13 ручных, 4 переключения между системами, 2 точки ожидания без статуса**.  
* Ни один шаг не порождает данных для измерения: времени до фидбэка, разброса оценок и доли просрочек **сейчас никто не считает** (подтверждено на Q\&A).  
* Системных попыток автоматизации не было. Обходной путь через публичные модели закрыт нормативно.

## **3\. Обязательные требования кейса vs наши предположения**

| Требование кейсодателя (проверено) | Наше предположение (нужно подтвердить) |
| ----- | ----- |
| Распределение работ с учётом объёма курса и нагрузки ревьюера | Полезнее распределять **внимание**, а не нагрузку: очередь работ по уровню неопределённости (чтобы ревьюер заранее мог оценить сложность проверки работы) |
| Предварительное ревью по заданным критериям \+ рекомендации | Экран ревьюера — это **полная работа с цветной разметкой фрагментов** и разбалловка сбоку, где балл по каждому критерию уже проставлен и редактируется.  Итоговая саммаризация собирается из пометок **после** правок ревьюера; все баллы подтверждаются одной кнопкой и уходят в ведомость |
| Фиксация результатов проверки | Единый контур: пометки → баллы → саммаризация → ведомость, с выгрузкой ведомости в Google Sheets и комментариев в Google Docs |
| Сигналы генеративного ИИ с уверенностью и основаниями; ревьюер подтверждает или отклоняет | Процессные сигналы (история коммитов, кросс-совпадения в потоке, похожесть с полностью ИИ работой) точнее и объяснимее текстовых детекторов |
| Не менее трёх дополнительных функций | Берём: триаж очереди, статусы и апелляция для студента, панель согласованности ревьюеров |
| Итоговая оценка и спорные случаи — за человеком | Число точек, где решение влияет на студента, **не меняем**: их остаётся три |
| Google Sheets **вне MVP** как рабочее место (уточнено на Q\&A) | Ведомость живёт внутри сервиса, Sheets и Docs — форматы выгрузки |
| Эталонных решений нет, сравнение только по критериям | Роль эталона играют калиброванные примеры уровней из репозитория |
| Критерии не меняются в середине курса, правки — в бэклог | Рубрика \= версионируемый конфиг, факты привязаны к версии |
| Один канал для MVP, масштабирование показать | Канал MVP — GitHub; ближайшие — Stepik, Google Docs, **Anytask** |
| Только реально доступные модели и сервисы, данные не в публичные API | Каскад моделей в контуре РФ или локально; ориентир бюджета $200–300 в месяц |
| Метрики: время, скорость фидбэка, расхождение ±1 балл, ошибки системы | Добавляем guardrail-метрики против штамповки и коридор правок 20–40% |
| Не строить второй Stepik | Мы делаем **рабочее место ревьюера**, а не платформу обучения |

## **4\. Что знаем о данных и доступах**

**Есть:** репозиторий github.com/ai-talent-hub-avito/homework\_examples — задания по восьми направлениям (data\_analysis, data\_science, GO, product, product\_business\_models, product\_fraud, system\_design, tech\_QA). Для каждого: условие, критерии с весами, плюс решения трёх уровней — слабое, среднее, хорошее. Это фактически **готовая разметка** и наш evaluation-датасет. Форматы: md, docx, pdf, ipynb, xlsx, html; часть решений — из нескольких файлов, анализировать вместе.

**Нет:** реальных ведомостей с историей оценок, замеров времени на работу, ставки эксперта, выгрузки обращений студентов. Всё это в вопросах ниже.

**Ограничения:** нельзя передавать код, условия заданий и персональные данные в публичные API. Допустимо локальное развёртывание или приватный изолированный контур. Отдельный риск — секреты и контакты, случайно оставленные студентами в работах: нужен фильтр до отправки в модель.

## **5\. Аналоги и чем отличаемся**

| Аналог | Что умеет | Почему не закрывает наш кейс |
| ----- | ----- | ----- |
| Gradescope (Turnitin) | Рубрики, группировка похожих ответов, автогрейдер кода | Живёт внутри LMS; ключевые функции только по институциональной лицензии; данные вне контура |
| CodeGrade / Codio | Автотесты, построчный фидбэк, детекция сходства кода, интеграция с Canvas и Moodle | Нет оркестрации внешних ревьюеров, дедлайнов, статусов, апелляций; нет учебных критериев с весами поверх процесса |
| CodeRabbit / Greptile | Автоматическое ревью pull request'ов, инлайн-комментарии | Оценивают по инженерным стандартам, а не по рубрике курса; нет баллов, ролей и педагогики |
| Антиплагиат.ВУЗ, GPTZero, JPlag | Заимствования и модуль ИИ с разбивкой по фрагментам | Сигнал без объяснения и без встроенности в процесс ревью; высокая и неравномерная ошибка первого рода |
| Anytask | Курсы, задачи с баллами, сроки, сдача на ревью, комментарий преподавателя | Нет рубрики как объекта, предварительного ревью, распределения нагрузки и аналитики. **Не конкурент, а свободный слот для надстройки и наш канал масштабирования на вузы** |

**Чем отличаемся:** единственные закрываем связку «мультиканальный приём → рубрика как конфиг → оркестрация внешних экспертов → объяснимые сигналы честности → накопление калибровки» внутри периметра заказчика. Ядро — аннотационный слой: ревьюер правит пометки на тексте работы, а фидбэк студенту собирается **только** из подтверждённых пометок.

## **6\. Гипотезы**

| \# | Гипотеза | Как проверяем | Правы, если |
| ----- | ----- | ----- | ----- |
| **H5** **самая рискованная** | LLM с рубрикой и тремя калиброванными примерами устойчиво различает слабое / среднее / хорошее решение | Прогон всех троек из репозитория, 3 повтора, две модели — **сегодня-завтра** | Порядок уровней верен в ≥80% троек; разброс балла между повторами ≤1; ≥90% замечаний с якорем на фрагмент |
| H1 | Больше половины времени ревьюера уходит не на суждение, а на вход в задачу | 3–5 интервью с ревьюерами и ассистентами вузов | Большинство называет подготовку дискомфортнее оценки |
| H2 | 50–70% работ очевидны и не требуют экспертного времени | Распределение уверенности модели на датасете | Выраженные полюса, уверенная классификация крайних случаев |
| H3 | Разброс оценок между ревьюерами значим | Данные Авито \+ двойная проверка выборки | Расхождение подтверждается хотя бы на одном задании |
| H6 | Ревьюер быстрее правит черновик, чем пишет с нуля | 5 ревьюеров, 2 работы с черновиком и 2 без | Медианное время −30%, 4 из 5 выбирают режим с черновиком |
| H8 (AI) | Процессные сигналы честности точнее и объяснимее текстовых детекторов | Примеры из репозитория \+ синтетика | Доля признанных ревьюером обоснованными выше, чем у текстового детектора |
| H11 | Аннотирование быстрее свободного текста при 5+ замечаниях и медленнее при 1–2 | Замер на двух типах заданий | Время падает на длинных работах и растёт не более чем на 20% на коротких |

Если H5 не подтверждается — предварительное ревью выпадает, продукт переопределяется в сторону триажа и оркестрации без генерации оценки.

## **7\. Открытые вопросы кейсодателю**

1. Сколько минут в среднем уходит на одну работу и сколько работ в неделю у одного ревьюера? Нужно для baseline. **10-15 минут с агентом у Игорят (профи), у остальных около часа на одну работу**  
2. Ориентировочная стоимость часа внешнего эксперта? Нужно для ROI. **от 1000 до 3000 за дз**  
3. Есть ли выгрузка оценок с историей ревьюеров, чтобы посчитать текущий разброс между ревьюерами? **есть**  
4. Какая доля обращений студентов в чат курса — организационные, а не содержательные? **редко спрашивают содержательные вопросы, 80% организационных, много на старте**  
5. Верно ли, что фиксация в Sheets вне MVP и достаточно фиксации внутри сервиса плюс экспорт? **нужна ведомость дл ревьюера с дедлайнами и домашками, с которой будет перекидывать на основной экран**  
6. Есть ли уже процедура апелляции и кто по ней принимает решение? **кейсы редкие, но бывают, проблемы нет, неудачная гипотеза**  
7. Что для вас будет признаком удачного пилота, помимо сэкономленных часов? **время, деньги, сокращение времени цикла проверки дз, качество\!\!**  
8. Распознавание картинок нужно ли? **На технических это оч редко, можно добавить в продуктовые прогаммы**  
9. Нужно ли сравнивать работы студентов между собой?? **Редкая ситуация, не фокус**

## **8\. Команда и как используем ИИ**

| Роль | Кто | Зона ответственности |
| ----- | ----- | ----- |
| Продукт и аналитика | Алиса | Проблематика, гипотезы, метрики, модель данных, презентация |
| Бэкенд и оркестрация | — | Коннектор GitHub, распределение, статусы, API |
| Агент и промпты | — | Рубрика как конфиг, аннотации, сигналы честности, evals |
| Фронтенд | — | Аннотационный экран ревьюера, ведомость, кабинет студента |
| Интервью и данные | Вместе | Разговоры с носителями проблемы, baseline-замеры |

**Где используем ИИ:** deep research по аналогам, разбор материалов кейса, суммаризация интервью 

**Что не делегируем:** разговор с носителем проблемы, выбор самого рискованного предположения, решение о том, что именно проверяем, продуктовую метрику «помогло ли человеку» и честность в списке того, что не подтвердилось.
