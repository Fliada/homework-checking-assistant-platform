    task1.md

    Подготовить каркас Go-приложения: репозиторий, веб-сервер, окружение, роутер и первые тестовые ручки.

    1. Структура проекта

    • Рекомендации golang-standards/project-layout
    • Разделить код на cmd/, internal/, pkg/

    2. Запуск веб-сервера

    • HTTP-сервер стандартным пакетом http
    • Параметры из .env, порт — переменная PORT
    • Переопределение через флаги: go run cmd/main.go --port 3000

    3. Роутинг

    • GET /ping → 200, {"message":"pong"}
    • HEAD /healthcheck → 204 без тела

    4. Корректное завершение

    • SIGINT/SIGTERM → завершение через context и signal
    • В лог (stdout): Shutting down service-courier

    • Порт из флага важнее порта из env — это проверяется тестом
    • Close() вместо Shutdown(ctx) — не критикал, но балл за «через context» не ставим
    • Роутер любой: stdlib/chi/gin/echo
    Позиция программы по ИИ: сигнал — повод для вопросов на защите, не для снижения балла.

    Как предложение попадает в рубрику

    1. Флажок ревьюера с экрана проверки → бэклог v3 (сразу, с привязкой к работе и версии)
    2. Сервис прикладывает данные: доля правок агента по критерию, разброс между ревьюерами
    3. Эксперт принимает или отклоняет; принятые собираются в черновик v3
    4. v3 применяется к следующему потоку; баллы текущего остаются на v2

    Что говорит поток по ДЗ 1

    Флаги и graceful через context проваливает больше половины — сигнал для лекции, а не для смягчения критерия. Секреты в коде — 3 работы, найдены автоматически до отправки в модель.

    Правил ли ревьюер решение агента · ДЗ 1, 27 работ

    По каждому критерию: доля решений агента, которые ревьюер подтвердил без правок (зелёный) и с правками (жёлтый). Клик по критерию — распределение отличий справа. Нужно, чтобы понимать, где агент надёжен, а где критерий сформулирован плохо.

    Отличие итогового балла от балла агента

    Только работы, где ревьюер вносил правки. Δ = балл ревьюера − балл агента. Сдвиг влево — агент мягче, вправо — строже. Симметричный разброс — критерий неоднозначен.

    Что с этим делать

    доля правок > 35% и разброс симметричный → критерий в бэклог: формулировка или примеры уровней
    сдвиг в одну сторону → правка промпта или эталона, версия конфига агента
    правок < 10% при автотесте → кандидат на «очевидную» проверку без внимания ревьюера

    Принципы

    • Одно уведомление — одно действие. Кнопка в сообщении делает то же, что кнопка в сервисе: «Передать», «Дослать», «Применить».
    • Студент всегда знает новый срок. При просрочке ревьюера студент получает не «задерживается», а дату.
    • Эскалация по времени, не по настроению. T−48 → T−24 → T0 → T+24: координатор узнаёт в момент дедлайна, админ — через сутки, если не решено.
    • Сервис сначала предлагает решение, потом уведомляет: в сообщении координатору уже есть, кому передать работы и с каким запасом.
    • Нет спама: напоминания склеиваются в одно сообщение на человека в день, кроме T0.
